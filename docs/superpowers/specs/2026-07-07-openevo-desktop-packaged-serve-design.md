# OpenEvo Desktop Packaged Serve Design

Tracked by #63.

## Goal

Make an installed OpenEvo package expose a single local Desktop entrypoint:

```bash
openevo desktop serve
```

The command starts one local FastAPI/uvicorn process that serves both:

- the existing OpenEvo Desktop sidecar API under `/openevo-api/*`;
- the built Desktop SPA from packaged static assets under `/openevo`.

This is the first release-shaped Desktop entrypoint. It deliberately does not
add Electron, Tauri, OS installers, code signing, native menus, or background OS
service management.

## Current State

OpenEvo already has:

- a typed sidecar API in `src/openevo/sidecar/api.py`;
- `openevo sidecar serve`, which serves only API routes;
- a Vite React app in `web/`, with `/openevo` as the Desktop route and
  `/openevo-api` proxied to the sidecar during development;
- `web/dist/`, generated by `npm run build`, but not packaged as `openevo`
  package data.

That leaves ordinary users with a development-shaped launch path: run a Python
API server and serve UI assets separately. The packaged serve slice removes that
split while preserving all existing sidecar behavior.

## Approach

Add a small `openevo.desktop` package with two responsibilities:

1. Locate packaged static assets.
2. Wrap an existing sidecar FastAPI app with Desktop static routes.

The static assets live under:

```text
src/openevo/desktop/web/
```

The source of truth for those files is still `web/dist/`. Build/release tooling
copies the Vite output into `src/openevo/desktop/web/` before building the Python
package. This spec does not introduce a Node build step inside `pip install`.

The packaged app serves:

| Path | Behavior |
|---|---|
| `/openevo-api/*` | Existing sidecar API routes. |
| `/assets/*` | Static bundled Vite assets. |
| `/openevo` | `index.html`. |
| `/openevo/*` | SPA fallback to `index.html` unless the path is an existing static file. |
| `/tasks`, `/tasks/*`, `/sessions`, `/sessions/*`, `/compare` | SPA fallback for the packaged bundle's existing visible client routes. |
| `/` | Redirect to `/openevo`. |

Static serving must not intercept `/openevo-api/*`, and missing static assets
must fail with a clear local packaging/build error rather than silently starting
an API-only service.

## CLI

Add a new top-level command:

```bash
openevo desktop serve [options]
```

Options mirror the common sidecar serve options where they matter:

- `--host`, default `127.0.0.1`;
- `--port`, default `3766`;
- `--config` and `--remote-profile`, optional pair for config-backed sessions;
- `--transport`, `dry-run` or `ssh`, default `dry-run`;
- `--desktop-config-root`, same behavior as `sidecar serve`;
- `--static-root`, optional override for tests, development, or custom packages.

The command builds the same sidecar session as `openevo sidecar serve`, wraps it
with Desktop static routes, prints a local URL such as
`http://127.0.0.1:3766/openevo`, and runs uvicorn.

`openevo sidecar serve` remains API-only for integration tests and power users.

## Packaging

`pyproject.toml` includes package data for:

```text
openevo/desktop/web/**/*
```

The Python package cannot rely on repository-root `web/dist` after installation.
Tests should prove that the package-data patterns include the Desktop static
asset path.

The repository should keep a packaged asset set copied from the current Vite
`web/dist` output so editable installs and wheels can exercise the local serve
path without relying on a repository-root `web/dist` at runtime. Release builds
must refresh this directory from a fresh `npm run build` before publishing.

## Error Handling

If no static root is available, the `assets` directory is missing or empty, or
`index.html` references a missing `/assets/*` file, `openevo desktop serve`
exits non-zero and tells the user to build/package Desktop assets, for example:

```text
OpenEvo Desktop static assets were not found. Run `cd web && npm run build` and
copy `web/dist` into `src/openevo/desktop/web` before packaging, or pass
`--static-root`.
```

If `--config` is supplied without `--remote-profile`, or the reverse, the command
uses the same validation error as `sidecar serve`.

API mutation-token behavior is unchanged because the packaged app reuses the
existing sidecar app object.

## Testing

Focused tests cover:

- packaged static root discovery;
- clear failure when static assets are missing;
- `create_desktop_app()` returns `/openevo`, `/openevo/*`, `/assets/*`, and
  `/openevo-api/desktop/shell` correctly;
- `/` redirects to `/openevo`;
- `openevo desktop serve` builds a wrapped app and passes it to the existing
  uvicorn runner;
- `--static-root` override works in tests;
- `pyproject.toml` includes `openevo` package data for Desktop web assets.

Web tests still run from `web/`; this slice does not alter Vite routing.

## Non-Goals

This slice does not add:

- Electron or Tauri windows;
- native installers, auto-update, code signing, app icons, or file associations;
- a sidecar subprocess launched by a native shell;
- OS-level service supervision;
- remote vLLM, Polar gateway, Docker Compose, rollout server, or evolution
  worker daemon management;
- automatic Node/Vite builds during `pip install`.

Those are later release-engineering layers on top of this local serve command.

## Self-Review

- No placeholder requirements: every path, command, and failure mode is explicit.
- Scope is one implementation plan: package static assets and add one CLI serve
  wrapper.
- The design preserves existing sidecar API semantics and does not alter remote
  lifecycle behavior.
- The design makes the final Desktop app more release-shaped without pretending
  to be a native installer.
