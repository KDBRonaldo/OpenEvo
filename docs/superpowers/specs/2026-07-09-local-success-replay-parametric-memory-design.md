# Local Success Replay Parametric Memory Design

Issue: #32
Date: 2026-07-09
Status: design approved for implementation planning

## Context

The current parametric-memory branch has a real controlled `train-fasttext`
positive result on local Qwen3.5:

- run root:
  `/tmp/tb21-task-local-parametric-trainfasttext-oneshot-20260709/eval-oneshot-r8-s260-pass2-cacheenv`;
- model: `Qwen/Qwen3.5-9B`;
- treatment adapter: `tb-parametric-memory-train-fasttext-oneshot-r8-s260`;
- controlled result: baseline pass@1/pass@k `0/1`, parametric-memory
  pass@1/pass@k `1/1`, delta `+1`;
- only `parametric_memory` was enabled; `text_memory`, `skill_bundle`, and
  `agent_system` were disabled.

The follow-up state-machine run was negative:

- run root:
  `/tmp/tb21-task-local-parametric-trainfasttext-statemachine-20260709/eval-statemachine-r8-s280-pass2-cacheenv-preloaded`;
- result: baseline `0/1`, parametric-memory `0/1`, delta `0`;
- failure shape: the adapter loaded and rewrote 64 LoRA keys, but the treatment
  made only one `tb_read_task` call; the second LLM response stopped without a
  `tb_exec` tool call and contained repeated planning text in Qwen `reasoning`.

The difference suggests that hand-written staged datasets are fragile. The
successful one-shot adapter's live trajectory is noisy, but it is valuable
because it was generated by the same local Qwen/vLLM/Harbor runtime used to
serve adapters during evaluation. Its `llm_calls.jsonl` contains exact
`input_messages`, `output_messages`, and tool specs for each live model call.

## Goals

- Add a task-local dataset path that distills successful local Qwen trajectories
  back into parametric-memory SFT records.
- Preserve the existing artifact boundary: the method still produces
  `ArtifactRegisterRequest(type="parametric_memory")` through
  `parametric_memory_lora_sft`.
- Use only local/proxy inference. The next real experiment should use the
  complete local `Qwen/Qwen3.5-9B` cache and GPU 7 unless a newer complete local
  Qwen cache becomes available.
- Keep the memory-only control: enable only `parametric_memory` during paired
  Terminal Bench eval.
- Avoid training stop/final-message behavior until a real successful local
  trajectory contains a verifier-passed prefix followed by a bad continuation
  that needs correction.

## Non-Goals

- Do not claim a full Terminal Bench 2.1 aggregate gain. This design targets
  selected task-local controlled experiments.
- Do not use subscription harnesses for parametric-memory evaluation.
- Do not train on hidden verifier answers or protected outputs.
- Do not add a new artifact type, gateway schema, or context-resolver branch.
- Do not make the `train-fasttext` state-machine dataset the default path; it is
  a rejected method iteration.
- Do not spend this iteration on incomplete local model caches. Current machine
  state shows `Qwen/Qwen3.5-9B` is complete, while
  `Qwen/Qwen3-30B-A3B-Instruct-2507` has incomplete blobs and
  `Qwen/Qwen3.6-35B-A3B` is not available in the active Hugging Face cache.

## Method Shape

Add a local-success replay projection to the existing task-local parametric
builder. The projection reads a successful Terminal Bench Harbor trial directory
that contains:

```text
agent/evolab_lab/.evolab/registries/trajectory/llm_calls.jsonl
agent/evolab_lab/.evolab/registries/trajectory/tool_calls.jsonl
```

For each selected LLM call, it emits one SFT record:

```text
prompt_messages = compacted input_messages from the live llm_calls row
response_messages = compacted assistant output message from the same row
tools = Terminal Bench tool schema
```

This is different from the current failed-prefix corrective builder. The
existing builder pairs failed prefixes with a target derived from a successful
Codex command. Local-success replay instead behavior-clones selected successful
local Qwen calls so the adapter learns the exact runtime prompt shape, tool
schema, and Qwen tool-call XML output distribution that vLLM serves.

## Record Selection

The first implementation should select only tool-call outputs. A usable row must
meet all of these conditions:

- `input_messages` is a non-empty list after compaction;
- the output has at least one assistant `tool_calls` entry;
- the output tool name is in an allow-list, initially `tb_read_task`, `tb_exec`,
  and `tb_run_tests`;
- the row can be tied to a successful trial whose Harbor result reward is 1.0;
- the resulting trace has the top-level Terminal Bench `tools` list so
  `tokenizer.apply_chat_template(..., tools=record["tools"])` remains aligned
  with runtime.

The default selector should reject no-tool assistant messages. That rule is
intentional: the state-machine run showed that final assistant-message examples
can pull the model away from tool execution.

The selector should expose simple filters:

- `allowed_tools`: default `["tb_read_task", "tb_exec", "tb_run_tests"]`;
- `max_records`: total cap;
- `max_records_per_trial`: cap per source trial;
- optional `require_tool_name` for focused follow-ups;
- optional `exclude_if_input_contains` and `exclude_if_output_contains` for
  known-bad artifacts such as malformed early exploration commands.

## Metadata And Lineage

Each exported record must include audit metadata:

- builder name: `terminal_bench_local_success_replay`;
- source trial directory;
- source trajectory id if available;
- source LLM call index;
- emitted output tool names;
- source model name from `llm_calls.jsonl`;
- prompt token count and completion token count when present in raw usage;
- selection filters used to produce the record.

The dataset manifest should record:

- source successful trial roots;
- task ids;
- record count;
- allow-list filters;
- model used for the source trajectory;
- base model intended for the adapter.

The worker job should keep using `parametric_memory_lora_sft` with
`training_projection={"type": "full_trace"}`.

## Experiment Plan

The first real experiment is `train-fasttext` v2b:

1. Build a replay dataset from the successful local Qwen trial
   `train-fasttext__7GGAsRu` under the one-shot pass2 run root.
2. Exclude no-tool assistant messages.
3. Start with tool-call rows only and cap the dataset to a compact replay of the
   useful solve portion. The first run may include the early noisy rows because
   they are part of the successful policy, but the manifest must record them.
4. Train a Qwen3.5 LoRA on GPU 7 with the same trainer used by prior
   `parametric_memory_lora_sft` jobs.
5. Run paired local Terminal Bench eval on `train-fasttext`:
   - baseline: `Qwen/Qwen3.5-9B`, no adapter;
   - treatment: same base model with the replay adapter;
   - only `parametric_memory` enabled;
   - verifier cache env set via `EVOLAB_TB_UV_CACHE_TARBALL` and
     `EVOLAB_TB_UV_PYTHON_TARBALL`;
   - no `--verifier-python-install-mirror`.

Success criteria for v2b:

- official paired eval completes without Harbor exceptions;
- adapter loads with rewritten Qwen3.5 LoRA keys;
- baseline remains `0/1` on `train-fasttext`;
- treatment reaches `1/1`, or if it fails, the failure trajectory contains more
  correct tool execution than the rejected state-machine adapter;
- GPU7 is released after managed vLLM teardown.

## Testing

Implementation should use TDD with focused tests in
`tests/evolution/test_terminal_bench_task_local_parametric.py`.

Required test coverage:

- parses a minimal successful local `llm_calls.jsonl` row into one full-trace
  SFT record;
- preserves `input_messages`, assistant `tool_calls`, and the Terminal Bench
  `tools` list;
- rejects no-tool assistant messages by default;
- records source call index, output tool names, model, and token usage metadata;
- exposes CLI flags for the local-success replay dataset/job path;
- writes dataset manifest and job payload compatible with
  `parametric_memory_lora_sft`.

Regression coverage should keep existing task-local final/sequence/schema-lock
builders unchanged.

## Risks

- The successful one-shot trajectory is noisy and may teach unnecessary
  exploration. The first replay run is still useful because it tests runtime
  alignment; a follow-up run can remove early malformed commands if the adapter
  reproduces them in evaluation.
- Tool-call cloning may overfit `train-fasttext`. The result should be reported
  as task-local parametric memory evidence, not generalization.
- Qwen3.5 single-GPU experiments are practical on this host, but newer Qwen3
  models require cache and serving validation before use.

## Approval

Proceed with implementation planning for the local-success replay dataset path,
then implement it behind opt-in CLI flags. Do not replace the existing
task-local builders or make replay the default until at least one controlled
paired eval is complete.
